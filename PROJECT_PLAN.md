# План личного Telegram-бота для поиска автомобилей

Дата исследования: 28 сентября 2026 года.

## Решение

Рекомендуется отдельное небольшое приложение на Python с aiogram и SQLite, работающее на домашнем Windows-ПК через long polling. Публичный сайт, домен, облачная база и Redis для этой архитектуры не требуются. Интернет необходим; во время выключения или сна ПК поиск и уведомления остановлены.

Репозиторий BottecRu/parser-daa-tg-bot использовать как технический референс, а не как подтвержденное готовое решение. Его копия находится в reference-parser-daa. Проверен код коммита fc1beb1c5ae955307ddc19894e6c92c3676655f3 от 26 июня 2025 года. Код не запускался; актуальная работоспособность парсеров не подтверждена.

## Что выяснено о репозитории

- bot/tg_bot.py: dp.start_polling(bot), публичный адрес для получения сообщений не нужен.
- WEBSITE_URL применяется к переходу на веб-интерфейс объявлений. /all_ads не реализует выдачу всех результатов внутри Telegram.
- Django используется непосредственно ботом и менеджером парсеров для работы с моделями БД, а также для админки и сайта. Удалить зависимость без изменений кода нельзя.
- DJANGO_SECRET_KEY — локально сгенерированный секрет Django для криптографической подписи, а не покупаемый ключ API.
- PostgreSQL хранит пользователей, фильтры и объявления. В UserFilters применяются ArrayField; простой замены строки подключения на SQLite недостаточно.
- Парсеры через Selenium записывают объявления в Redis с TTL 1800 секунд. Бот читает Redis; ads_sync переносит данные в PostgreSQL. В текущей архитектуре Redis нельзя просто отключить.
- Парсеры стартуют с общих лент Avito, Drom и Auto.ru; это не полноценный поиск по произвольной модели на всех страницах каждой площадки.
- В users/models.py у UserFilters нет поля model; в bot/utils.py отсутствует отдельная проверка модели.
- bot/ads_sender.py использует общий ads:checked. Для повторного поиска после смены фильтра и учета доставки каждому пользователю логику нужно менять.
- ads/models.py использует глобально уникальный ad_id, а не пару platform + ad_id. Нужна защита от совпадений ID разных источников.
- ads/tasks.py подставляет время синхронизации в published_at через модель; его нельзя считать достоверной датой публикации на площадке. Очистка по умолчанию удаляет объявления старше семи дней по created_at.
- Docker Compose запускает семь сервисов, включая браузер. Для одного пользователя это заметно сложнее минимального приложения.
- Перед запуском исходника следует закрепить версии Docker-образов, исправить разбор DEBUG, ограничить сетевую публикацию портов, убрать чужие адреса из настроек и последовательно удалить webhook до старта polling.

Исходный проект: https://github.com/BottecRu/parser-daa-tg-bot

## Доступ к данным

1. Drom документирует GET https://api.drom.ru/v1.2/bulls/search с фильтрами модели, цены, региона и других параметров. Документация сама по себе не подтверждает свободный доступ для стороннего бота, стоимость, квоты или полноту. Уточнить условия и проверить доступ до выбора API основным источником.
2. Auto.ru требует токен, получаемый у менеджера. Наличие API не подтверждает возможность получить всю поисковую выдачу. Уточнить именно получение чужих актуальных объявлений по фильтрам, стоимость, квоты и право хранения данных.
3. Avito: доступ к подходящему официальному API поиска и его стоимость не подтверждены. Официальный каталог не удалось прочитать через инструмент исследования. Не планировать получение всех объявлений только на основании наличия Business API.
4. Юла: подходящий публичный API поиска не подтвержден. Официальная справка о профиле предупреждает о блокировке за сбор информации скриптами. Подключение отложить до подтвержденного способа доступа.
5. Если API недоступен, отдельно оценить разрешенный доступ к страницам либо поставщика данных. Подписка на интерфейс агрегатора не равна лицензии на его API.

## Этапы и критерии готовности

### 1. Проверка одного источника — до построения полного бота

Взять BMW X5 как контрольный запрос, задать регион, цену и годы. Начать с проверки Drom, затем Avito и Auto.ru. Выбрать API или допустимый способ получения страниц. Проверить несколько страниц выдачи, ссылки, модель, цену, регион, поведение при пустом результате и ошибке доступа.

Результат: хотя бы один источник возвращает реальные подходящие объявления; ограничения и разрешенный способ доступа записаны. Если ни один источник не проходит проверку, сначала решать получение данных, а не строить интерфейс вокруг фиктивных результатов. Блокировка источника должна отличаться от нулевого количества объявлений.

### 2. Минимальный локальный бот

Python + aiogram 3.x, SQLite, HTTP-клиент для API/страниц; браузер подключать только при необходимости. Отдельные модули sources, search, storage и telegram. Версии зависимостей закрепить после проверки совместимости.

Создать бота через https://t.me/BotFather командой /newbot. Сохранить токен в локальном .env, исключенном из Git. Ограничить доступ Telegram ID владельца. ID можно получить собственным ботом. Создать виртуальное окружение и понятный start.ps1. Отдельные регистрации для SQLite, Django и Redis не нужны.

Результат: /start отвечает с ПК, посторонние пользователи не получают доступ, повторный запуск сохраняет настройки. При существующем webhook сначала выполнить его удаление, затем запускать polling; решение о сбросе накопленных сообщений принимать явно.

### 3. Поиск внутри Telegram

Фильтры: марка, модель, город/регион, цена от/до, год от/до, пробег до. Сначала ввод через кнопки и поля; свободный текст и AI не обязательны. Поиск возвращает карточки с ценой, годом, пробегом, городом, источником и исходной ссылкой. Кнопки: следующие результаты, обновить, сохранить поиск.

Первый запрос собирает существующие объявления в пределах явно заданного лимита страниц. Результаты кешируются. Показывать время последнего обновления и состояние каждого источника. Не обещать полное покрытие всех объявлений.

Результат: BMW X5 отбирается по модели; выдача и пагинация работают целиком в Telegram, после перезапуска доступны сохраненные поиски.

### 4. Мониторинг

Фоновая проверка сохраненных поисков с интервалом, выбранным по ограничениям источника. Первичная выдача и последующие уведомления разделены. Объявления идентифицировать парой (source, external_id), доставку — пользователем, поиском и объявлением. Сохранять first_seen, last_seen, время проверки, исходную дату публикации только при наличии, историю цены и состояние отправки.

Результат: повторная проверка и обычный перезапуск не повторяют уведомления; изменение цены обрабатывается отдельно; временные ошибки имеют задержку повторения. При неоднозначном сетевом сбое отправки Telegram возможны повторы, поэтому абсолютную гарантию exactly-once не обещать.

### 5. Второй и третий источники

Добавлять Avito и Auto.ru последовательно после независимой проверки доступности. Сопоставить марки, модели, валюту, километры и регионы. Ошибка одной площадки не должна останавливать остальные. Одинаковые машины на разных сайтах сначала помечать как возможные дубли, не скрывать автоматически по совпадению названия и цены.

Результат: единая выдача хотя бы с двух площадок и независимые статусы источников. Юла — отдельный последующий этап.

### 6. Эксплуатация на ПК

Проверить работу в течение нескольких дней, сон ПК, пропадание интернета, перезапуск, ротацию логов и резервную копию SQLite. По желанию настроить Планировщик заданий Windows. Круглосуточный режим позже переносится на сервер; polling при этом по-прежнему не требует домена.

## Если все же адаптировать исходный репозиторий

Сохранить Django, PostgreSQL, Redis и Selenium; использовать Docker Desktop с Linux-контейнерами/WSL2. Подготовить .env, сгенерировать собственные пароли и DJANGO_SECRET_KEY. Сначала поднять БД и Redis, выполнить миграции и createsuperuser, открыть локальную админку, добавить активный источник drom. Затем запустить браузер, один парсер и бота, проверить результат. Остальные источники включать по одному. WEBSITE_URL убрать из пользовательского сценария, заменить /all_ads выдачей в Telegram. Далее исправить ограничения модели, поиска, дедупликации и доставки, перечисленные выше. Домен и облачные регистрации не нужны.

## Оценка трудозатрат и расходов

Оценка для одного разработчика при доступном источнике: первичная проверка 1–3 рабочих дня; минимальный бот с одним источником 3–7 дней; несколько источников с мониторингом ориентировочно 2–4 недели суммарно. Ожидание доступа к API, изменения сайтов и блокировки в эти сроки не гарантированно укладываются.

Для локального варианта: домен 0 рублей, аренда сервера 0 рублей, стандартные сообщения Telegram без оплаты в пределах лимитов, SQLite без облачной подписки. Интернет, электричество и время разработки остаются расходами. Стоимость данных, API и возможных внешних сервисов пока неизвестна; нулевой общий бюджет обещать нельзя. Покупки до проверки источника не требуются.
